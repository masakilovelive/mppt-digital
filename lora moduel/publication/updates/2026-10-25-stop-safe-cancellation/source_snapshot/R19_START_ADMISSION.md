# R19 高速開始の受付条件と測定仕様

更新日: 2026-10-25 JST

高速開始の計画判定と実機での開始成立を区別する。今回のオフライン修正は、両側の500 ms条件を同時に満たせる計画の検査と、根拠のない高速開始・成功判定の防止を対象とする。次のGrantを事前予約して発行する機器側の仕組みは未実装であり、本修正だけでは実機の高速開始は可能にならない。

## 維持する条件

| 境界 | 条件 |
|---|---|
| Ground | 完全な元のPARAM_REQUEST_LIST受付から、厳密に新しいGrant受信まで500 ms以内 |
| Vehicle | 同一Grantの物理送信完了から、完全かつ正当なVCBN開始要求受付まで500 ms以内 |
| Groundの送信方向切替え | Grant受信後の100 ms guardを短縮しない |
| USB製品Heartbeat | 106 msの公開完了条件を維持 |
| セッションと取得 | 元の要求受付を起点とする28秒leaseと30秒取得条件を維持 |
| 要求回数 | 最大1回。部分書込み・例外・期限切れでも再要求しない |

Grantを既に観測した後で要求を受けた場合、そのGrantはbaselineであり、新しいGrantとして再利用しない。同一ミリ秒でも、要求とGrantの実行順序が不明なら開始可能とは判定しない。

## 計画の検査

各イベントの時刻を単一点ではなく、根拠のある最早・最遅時刻の範囲で扱う。Groundの要求受付と次のGrant受信はGroundの時計、VehicleのGrant送信完了とVCBN受付はVehicleの時計で比較する。別の時計を直接引き算しない。

最も早い要求受付から最も遅いGrant受信までが500 ms以内であり、最も早いVehicle送信完了から最も遅いVCBN受付までが500 ms以内であることを必要条件とする。Groundの100 ms guard、通信・処理時間の上限、時計対応の誤差を含める。上限が不明な時間を0として代入しない。

計画はslotの識別子、USB epoch、Grantのsessionとcycle、baseline、元の要求時刻に結び付ける。未使用・有効期間内・新しいGrantという条件を失った計画は採用しない。

計画計算の合格は「数値条件の下で成立可能」を意味する。入力の自己申告フラグやJSONは、実機の予約成立、認証、RF到達、書込み許可の証拠にはならない。

## 測定ツールの扱い

既存の低速診断による取得台帳は維持する。高速開始を要求する新しい経路では、ARMのPC書込み受付とHeartbeat受信だけでPARAM要求を送らない。受付理由・見送り理由・時刻・照合対象を保存し、高速計画を評価するオフラインシミュレーションと、実機操作を分離する。

現行候補には有効な将来slotを生成・公開する能力がない。そのため高速開始指定の実機実行は、許可消費・COM・JTAG・書込みより前に拒否する。架空のslot、固定待機、過去のGrant周期、Heartbeat件数で代用しない。

取得台帳に932件が揃うこと、Heartbeatが継続すること、診断取得とR18復旧が成功することは、それぞれ高速経路の成立とは別の結果である。低速への切替えを高速成功に含めない。

## 次に必要な機器側の予約機構

実機で受付条件を成立させるには、Vehicleが次のGrantの機会を予約し、Groundへ検証可能な有効範囲と識別情報を渡す必要がある。通常TDDの固定5秒計算では、AUX・送信drain・Heartbeat・遅延terminalによる変動を保証できない。

予約は少なくともboot/session、Grant cycle、writer tokenとgeneration、元の要求bytesとUSB epoch、有効期間、schemaとroleに結び付け、1回だけ消費する。reset、generation変更、AUX Busy、拒否・部分書込み、送信待ち量やHeartbeatによる予定変更時は失効させる。この機構のwire形式と状態遷移は本修正では追加しない。

その後の実機試験では、元の要求受付・新しいGrant受信・同一Grantの物理送信完了・完全VCBN受付・交渉完了・bulk開始を取得する。実際のイベントで両500 ms条件を再検証し、同一runで932/932件・30秒以内・Heartbeat最大2,500 ms以下・全error 0を確認する。
