# R19時刻応答修正と通信停止の切分け

2026年10月24日JSTの進捗です。VehicleのUSBローカル時刻応答を実装し、両機の時刻応答を実機で確認しました。一方、最新の比較試験ではGroundがAUXのHIGH復帰待ちで安全停止しており、R19の通信障害解消・高速通信の受入には至っていません。試験終了後は両機をaccepted R18へ復旧しています。

## 解消した問題と残る問題

Vehicleには、測定ツールが要求するUSBローカル時刻応答handlerがありませんでした。この役割契約の不一致を修正し、役割ごとの機能契約を検証する試験を追加しました。現在はVehicle・Groundとも時刻応答が成立しています。[修正と検証記録](evidence/clock_fix/summary.json)

過去に直したAUX問題は、USB診断の早期returnによって通常のAUX観測が止まる経路です。観測継続の改善は確認済みですが、E220の物理信号が常に所定時間内にHIGHへ戻ることまで保証する修正ではありません。

最新試験ではGroundの32 byte UART書込みが全量受理された後、MCU時計11.744069秒でAUXの安全停止を記録しました。停止通知は、意図的なPC読取り休止より19.8455222秒前に、同じPC時計で受信されています。したがって、この停止を今回の読取り休止が引き起こしたとは説明できません。停止時の最大観測間隔は100.561 msで、割込み履歴にもoverflowがあり、物理LOW継続とHIGH見逃しの最終分離はできていません。

USBの既存対策は「送信可能になったのに残りデータの送信を再開しない」特定の待機状態を対象とします。今回の初回診断失敗は、先行データが残り、送信世代と取出し世代が1つずれ、IN_EMPTY割込みが有効な状態です。以前の単純なidle再開漏れと同一条件ではありません。[USB状態の比較検証](evidence/usb_cause/summary.json)

「再発」は同種の停止・タイムアウトを再検出した意味であり、既知の同じバグが再発したと確定した意味ではありません。今回のUSB診断失敗はVehicleがPC読取り開始前、Groundが名目上の時刻対応では終了後に位置しますが、時計のドリフト保証がないため、起動・終了処理との物理的な因果は未確定です。通常運転中の製品USB障害と同一視しません。

## 読取り休止と再開の比較

PC測定ツールへ読取り開始・停止・worker終了・COM closeの時刻記録と、Groundだけを一度休止する機能を追加しました。40.0123527秒の測定中、約20秒後から2,005.6241 ms休止し、同じ接続・同じ読取り担当で自動再開しています。休止中のRead呼出し回数は726から726で変化せず、再開した最初のReadで診断2フレーム126 byteを回収しました。

Vehicleは2,674 byte、Groundは2,677 byteを保存し、各43フレームのCRCを検証しました。CRC異常・ノイズ・末尾部分フレーム・読取りエラーは0でした。これはUSBで観測した診断等のフレームの結果であり、無線や製品通信の全error 0を証明する結果ではありません。内部記録32件・16ペアも照合しています。[独立評価](evidence/current/independent_review.json)

WindowsやドライバーはアプリのRead休止中にも先読みできるため、今回の休止はUSB物理IN転送を止めた証明ではありません。外側手順のPASSは比較手順・記録取得・R18復旧の完遂を示し、製品受入のPASSではありません。

## 次の確認と受入条件

先行したAUX停止について、HIGH復帰の観測・状態判定と物理信号を切り分ける必要があります。USBは起動・測定中・終了の段階を区別し、必要な時点の取出し・完了記録を取得します。106 ms、AUXの2,000 ms、HIGH安定15 ms、UART、TDD、E220設定は緩和しません。

最終受入は同一runで932/932件・30秒以内・Heartbeat最大2,500 ms以下・全error 0を満たすことです。両試験の一回限定許可は使用済みで、R19の製品受入・Deploymentは未許可です。公開された過去の記録は実機操作の新しい許可にはなりません。

今回の公開物にはapplication BIN、ELF、MAP、EXE、APIキー、実行許可ファイル、operator確認全文、巨大な生データダンプを含めません。原本のローカルパスは来歴であり、移植先の設定として使わないでください。
